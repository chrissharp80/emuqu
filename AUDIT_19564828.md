## 1. A preservation step fails silently, then the code overwrites or advances anyway

**Cited instance: CONFIRMED [V].**
- `RawRRBackup+Streaming.swift:145` swallows the open error (`try? FileHandle`).
- `:182-184` handles the failed read by calling `preserveCorruptedPointsFile`, then returns `false`.
- `:216-220` only logs a failed move. The function returns `Void`, so the caller cannot tell.
- `:156` is a non-atomic write of the new batch alone over the original path.
- `:27` then advances `backedUpCount` to `points.count`.
- The aside name has one-second resolution (`:213`), so a second failure in the same second collides with the first and the move fails.

Additional instances:

1. **[V] `SettingsManager.swift:176, 184-193, 322-328`.**
   - On any read or decode error except protection code 257, `preserveUnreadableFile` deletes the previous backup and copies the file aside. A copy failure is only logged.

   - Result: the next settings change writes defaults (`.atomic`) over the user's real file, with no copy kept.

## 2. Plaintext fallback not registered for re-encryption, or repair drops it

**Cited instance: CONFIRMED [V].**
- `Streaming:96, 107-122` writes plaintext lines when the key is unavailable and only logs it.
- It makes no ledger call.
- The one-shot path (`RawRRBackup.swift:361-375`) registers the plaintext and uses the stricter `.completeFileProtection`.
- The repair could not fix streaming files even if they were registered: `reencryptBackup` (`:404-408`) clears any row with `fileName == nil`, and every streaming row has `fileName == nil`.
- Plaintext persists in exactly the crash or interrupted-night case, because a normal stop replaces the stream with a one-shot backup.

Additional instances:

1. **`RawRRBackup.swift:404-408`.**
   - `reencryptBackup` never calls `mergeIndexIfLaunchReadFailed`.
   - If the launch read of the index failed while the key is available, every pending raw-backup id is cleared and the plaintext files remain.
   - On the next launch, `migrateExistingFileProtection` then downgrades those files from `.complete` to until-first-unlock.
2. **[V] `Archive+PendingEncryption.swift:110-119` with `Archive.swift:599-605`.** A pending id missing from the in-memory index is cleared from the ledger. This hits:
   - plaintext sessions moved to `Trash/`
   - sessions moved to `QuarantinedDuplicates/`
   - every pending id, when the index is empty or partial at migration time
   - pending ids belonging to *another* archive: the ledger is process-global, so `runDeferredMigrations` on a temporary or test archive clears the host app's real entries (see §5)
3. **`Archive+IndexIO.swift:96-133` with `Archive+PendingEncryption.swift:36-40`.** The protection-downgrade walk is recursive, but its pending check matches only `<uuid>.json`. A plaintext `Trash/<id>.session`, or a quarantined file, is downgraded while its id is still pending.
4. **`RawRRBackup.swift:379-385`, `Streaming:34-39`.**
   - The ledger is keyed by session, not by file.
   - When removing a superseded plaintext file fails, that file stays on disk.
   - A later encrypted write for the same session clears the ledger entry, and the orphan file is downgraded.
5. **`WorkoutTrackBackup.swift:365-368, 496`.** GPS tracks and per-second samples are always plaintext JSONL with until-first-unlock protection. This is by design, but it sits outside both app-layer encryption and the ledger.

Checked and correct: CloudKit payloads and CKAsset temp files fail closed; `UIStateCache` fails closed; the assistant stores use `.completeFileProtection`.

## 4. AI streams: "completed reply" defined differently per provider

**All six cited claims CONFIRMED.** The fallback half is narrower than the review states. Fallback happens only when Apple Intelligence is the selected model and Routing is Auto or Deep (`TurnRouter.swift:313`). With a cloud model picked, there is no fallback at all.

The root cause is that `AIStreamEvent.done` is optional and carries no stop reason. `ProviderStream.run` (`:35-40`) and `drain` (`AssistantViewModel+Tools.swift:216-232, 308`) accept any normal close.

1. **`OpenAICompatibleStreamer.swift:347-359`.** OpenAI, Grok and DeepSeek accept a clean EOF with no `[DONE]` or `finish_reason` as a complete reply.
2. **`GeminiProvider.swift:280-281, 320-333`.** Gemini does the same, and also yields `.done` for a cut stream.
3. **`GeminiProvider.swift:312-352`.** `finishReason` is never read. MAX_TOKENS, SAFETY, RECITATION and MALFORMED_FUNCTION_CALL all surface as complete or empty success. `blockedPrompt` is caught only when `candidates == nil`.
4. **`OpenAICompatibleStreamer.swift:394`.** Only `finish_reason == "tool_calls"` is read. `length` and `content_filter` look complete.
5. **`OpenAICompatibleStreamer.swift:352-353, 444-446`.** `[DONE]` flushes truncated tool arguments. `FactResolverRegistry.stringArgs` (`:512-516`) turns them into `[:]`, so the tool runs with default scope.
6. **`AnthropicProvider.swift:532, 461-465`.** A `max_tokens` stop in the middle of a `tool_use` emits `.toolUse` with truncated JSON. The "…" marker is then rewound (`Tools.swift:385`), and the tool runs anyway.
7. **`AnthropicProvider.swift:462-464`.** `pause_turn` is never resumed. Both it and `max_tokens` end the turn as success with "…", which is saved and replayed as history.
8. **`AnthropicProvider.swift:461-462`.** The `refusal` stop reason is not handled.
9. **Malformed JSON events are inconsistent.** OpenAI-compatible (`:370-372`) and Gemini (`:324-326`) skip them silently, so text or a `functionCall` drops from the middle of a reply. Anthropic (`:444-450`) throws. Anthropic also silently ignores valid non-object JSON (`:419`).
10. **`Routing.swift:303, 320-326`.** An empty reply is deleted with no error shown. In voice mode the recovery line requires `errorMessage != nil` (`Audio.swift:798-801`), so the user hears silence. Only Grok substitutes a message.
11. **`Context.swift:577-578` + `Tools.swift:531-535, 623, 630`.**
    - When text chat falls back after partial text, it keeps the failed provider's sentences and appends the fallback's full answer with no separator.
    - The whole bubble is then stamped with the fallback provider's badge.
12. **`AppleFoundationProvider.swift:549-550, 622`.** An Apple failure after visible output allows fallback, with the same mixed output as item 11.
13. **`AIProvider.swift:382-395, 574-578`; `AnthropicProvider.swift:433-435`.**
    - Every mid-stream error event becomes a fallbackable `.invalidResponse`, even after partial text.
    - A Gemini safety block is handed to another vendor, while an Apple guardrail never is.
14. **`Context.swift:581`, `Tools.swift:498-505`, `AIProvider.swift:150-199`, `Context.swift:138`.**
    - A failed partial reply is saved with no incomplete marker.
    - It is sent as complete history on the next request.
    - After a relaunch, nothing shows it was cut off.
15. **`Routing.swift:298-304, 723-728, 774-782`.** Fact extraction runs on failed and partial replies.
16. **`Tools.swift:130, 301`.** After the tool budget is exhausted, a final pass that emits only tool calls leaves an empty turn, which is deleted silently.
17. **OpenAI-compatible and Gemini accept a tool-only round with no terminal event.** Gemini parallel calls that would have come in a lost chunk are silently missing. Anthropic throws in the same situation.
18. **`Audio.swift:798-801`.** In voice mode, a partial reply is spoken as complete. On fallback, the content is duplicated aloud.
19. **`Context.swift:35-38, 271-276`.**
    - A truncated conversation summary is stored as `priorSummary`.
    - `summarizedThroughTurnID` advances, so the dropped turns are never summarised again.
20. **`OpenAICompatibleStreamer.swift:471-472` vs `AIProvider.swift:565`.** A 5xx maps to different errors per provider. Anthropic's mid-stream `overloaded_error` shows the raw message.
21. **`ProviderStream.swift:51-52`, `Routing.swift:665-666`, `Tools.swift:632`.** A system-initiated `URLError(.cancelled)` shows "Request cancelled." and does not stop the fallback chain. Low confidence.
22. **Usage accounting.**
    - Anthropic (`:483-491`) and Gemini (`:333`) record nothing on a cut stream.
    - OpenAI-compatible (`:375`) counts every chunk that carries `usage`.
    - Apple emits none.
23. **No end-of-stream tests.** No provider tells the chat layer a reply was truncated. `ProviderStreamTests` covers error mapping only.

## 8. RRCollector god object

**CONFIRMED.**
- 6,929 lines across 26 files.
- The "coordinators" are stateless `struct { let collector }` types, rebuilt on every access (for example `:151`).
- All state stays on RRCollector and its four sub-objects:
  - about 28 stored fields
  - 20 injected `let` dependencies
  - 32 sub-object fields
- It also resolves about 10 dependencies from the global container and holds 5 `UserDefaults` keys.
- The split also gets past `check_aggregate_type_size.sh`, which does not count sibling types.

Dead code:
- [V] `isDeviceFetchInProgress` is never set to `true`, so the view branches that read it (`RecordView+Sections:95`, `MorningResultsView:591`, `+DetailCards:108`) are unreachable.
- [V] `collector.backgroundAudioManager` is never read, yet it is resolved at init.
- `cancellables` is never used.

Shared state coupling the responsibilities:
- `isOvernightStreaming`: about 9 readers and 4 writers
- `isCollecting`: 7 writers
- `overnightDeviceBackupActive`
- `lastError`: about 20 writers
- `currentSession`
- `deviceStatus.isStreaming`: 5 writers. This refutes the "exactly ONE writer" comment at Bindings:23-24.
- `useDeviceBackupForOvernight`, `deviceFetchPolicy`, `streamingTimer`, `cachedTrainingLoad`, `morningStatus`

Correctness bugs found in these files:

1. **Stop, Pause and Discard can each run twice for the same night.**
   - Their guards check only `isOvernightStreaming`, then `await` before the flag is cleared (OvernightStreaming:315/322, PauseResume:45/48, Discard:30/33).
   - `isOvernightEnding` is not checked, and the wait can last up to 15 s.
   - `PolarManager.stopStreaming()` returns the same points each time, so the night is processed and archived twice under conflicting states.
2. **A failed overnight analysis leaves `recordingPhase == .analyzing` permanently** (Gather:98; `analyzeAndFinalizeOvernight` and `finalizeFallbackSession` never reset it).
3. **During morning processing, `isOvernightStreaming` and `isCollecting` are already false** (Gather:95-99).
   - The night therefore appears in Lost Sessions and can be deleted (tombstoned) while it is being archived.
   - `strapRecordingBelongsToLiveSession` also turns false mid-download.
4. **Accepting a session overwrites a rescore that ran during review.** `finishRescore` never refreshes `currentSession`, so Accept archives the stale analysis (Acceptance:44).
5. **A late arming task can arm the strap after the night has ended,** without rechecking (Arming:141-144). *Plausible.*
6. **A pause whose archive write fails still publishes as paused** (PauseResume:155-158, 88, 109). The pre-pause segment is never merged.
7. **The async paused-state restore overwrites a recording that has already started** (PauseResume:322-340). *Plausible.*
8. **"Not while paused" is enforced only in the view.** A ≤5% battery reading during a live night could call `finalizeFromPause` (Bindings:208-213). *Plausible.*
9. **The baseline rebuild retries without limit** (`RRCollector.swift:615`).
10. **`resetSession` resets only part of the state and always clears the paused marker.** `acknowledgeError` during the short-pause window deletes a marker that was just persisted (`RecordView.swift:194`, OvernightStreaming:47-53).
