How reachability was computed

Starting from the app, watch and App Intent entry points, the call graph was walked through every resolved call. The graph is the recorded calls merged with calls, property reads, protocol dispatch and closure assignments found mechanically in the code; where a name matches several units every match is followed. A unit with an outside trigger (a SwiftUI body or action, delegate callback, notification observer, timer, Codable synthesis) counts as reachable only once its type is referenced by code already reached. Because readers record calls, not every property read, a second pass also counts a unit as reached when its name appears anywhere in code already reached. A unit is listed below only if both passes miss it, so this list errs toward leaving dead code out rather than listing live code. Test code was walked separately. Protocol requirements are not listed as unreachable.

Where this comes from

  • The records live in docs/codemap/records, one JSON file per source file. This page is generated from them by scripts/codemap/codemap.py report.
  • The first full set was written against main at 8d32097: a reader went through every line of every file and wrote one record per unit, and a second reader re-checked every record against the code. Line numbers quoted in findings refer to the code at the time the finding was recorded.
  • Each record stores a hash of the code it describes. scripts/check_codemap.sh fails CI when a unit has no record, a record has no description, or the code has changed since the record was written. A record is marked current only by re-reading the code and updating it.
  • The two string catalogs were audited key by key in the original pass and are not tracked by hash; the audit is shown under Strings.

What this does not do

  • Nothing was compiled or run. Every claim comes from reading code. Findings about runtime behaviour (races, timing, OS behaviour) are reasoned from the code, with file and line cited.
  • The CI check proves a record was written after the last change to its code. It cannot prove the description is correct; that rests on whoever updated it and on review.
  • Calls through protocols and stored closures are resolved to the implementations a reader could identify. Reachability combines the recorded call graph with a search for each unit's name in reached code, so the unreachable list errs toward leaving dead code out.
  • Severity is the reader's judgement against a fixed rule (high: wrong health numbers, data loss, privacy or billing breach, crash).
